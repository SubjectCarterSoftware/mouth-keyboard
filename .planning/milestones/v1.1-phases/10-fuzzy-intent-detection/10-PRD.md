# Phase 10 PRD: Fuzzy Intent Detection

We originally implemented voice command detection using rigid trigger phrases, specifically variants of "convert to" and "format to," followed by one of the supported output modes: Email, Slack, Teams, Action Items, or AI Prompt. The current approach depends on those phrases being spoken clearly and in the expected form, usually at the end of the dictated statement. In practice, that has proven too brittle for natural speech. People do not reliably say the same wording every time, speech-to-text may slightly alter the phrase, and filler words or small variations break exact matching too easily. I want to replace that architecture with a small intent-detection layer that uses normalization plus fuzzy matching over a fixed set of known output intents instead of exact phrase matching.

The new architecture should treat this as classification over a limited command set, not open-ended language understanding. The supported intents remain Email, Slack, Teams, Action Items, and AI Prompt. Each intent should have a canonical name plus a list of aliases and common phrase patterns. For example, Email might include patterns such as "make this an email," "turn this into an email," "rewrite as an email," "as email," or "email mode." Slack, Teams, Action Items, and AI Prompt should have similar phrase sets. The system should normalize transcripts before matching by lowercasing, trimming punctuation, collapsing whitespace, and standardizing obvious variants such as "e mail" to "email." It should also remove optional filler words around likely command phrases when appropriate, such as "okay," "please," "can you," "real quick," "uh," and "um."

Do not scan the entire transcript equally. The initial implementation should focus on likely command zones, especially the end of the transcript, and optionally the beginning as well. For example, inspect the first and last several tokens rather than the full body, because the command is most likely to be intentionally placed there. For each candidate zone, compare it against the known patterns for all supported intents using a hybrid scoring approach. First, check for exact normalized phrase matches or regex-style pattern matches. If that fails, apply fuzzy matching using string similarity (pure Swift implementation — no external library). The scoring should consider phrase similarity, token overlap, presence of the target keyword such as "email" or "slack," and a position bonus if the candidate appears at the beginning or end of the transcript. The matcher should then choose the top intent only if its score exceeds a threshold and also beats the second-best result by a minimum margin. If confidence is too low or ambiguous, do not auto-trigger a transformation.

Once an intent is detected, the system should remove the matched command span from the transcript and treat the remaining text as the actual user content to be transformed. That cleaned body, along with the detected target intent, should then be passed to the local LLM for light restructuring. The local LLM should not be responsible for command detection except as a possible future fallback for borderline cases. The command-detection layer should remain deterministic, fast, and local. The desired flow is: speech-to-text completes, transcript is normalized, likely command zones are extracted, those zones are compared against a fixed catalog of intent patterns, a best intent is selected if confidence is high enough, the matched command phrase is stripped, and the remaining text is sent to the local LLM with the chosen transformation target.

Implement this as a config-driven system rather than hardcoded one-off logic. There should be an intent definition structure for Email, Slack, Teams, Action Items, and AI Prompt, where each intent contains its ID, aliases, phrase patterns, and confidence threshold. Build the matcher so that it is easy to extend with more intents later. Start with a practical version that supports commands at the beginning or end of the utterance, uses normalization plus exact and fuzzy matching, and includes safe fallback behavior when the result is uncertain. The end goal is to replace brittle exact trigger matching with a more natural and resilient voice command architecture while keeping detection fast and predictable.

## Fuzzy Matching Implementation Note

RapidFuzz is Python-only. For Swift, implement string similarity directly (Jaro-Winkler or Levenshtein distance — ~50 lines of pure Swift). The fixed intent set is small enough that a bespoke implementation is appropriate — no external dependency needed.

## What Gets Rewritten

This phase replaces:
- `IntentDetector.swift` — current exact-phrase detector
- `ConvertMode.activationPhraseCandidates` — the hardcoded 4-variant phrase lists
- The `detect(transcript:modes:)` call site logic

The `ConvertMode` enum, `ConvertIntent` struct, `LLMRewriteService`, and `ActivationStore` wiring remain, but the detection layer is fully replaced.
